# Automotive Service Directory — Scraping & Data Pipeline

Навчальний DE-проєкт: збір даних про СТО/автосервіси з кількох українських
довідників і побудова інкрементального (CDC-подібного) завантаження в базу
даних без повторного перезаписування всього щоразу.

## Навіщо цей проєкт

Класична проблема при регулярному скрапінгу сайтів: джерело (HTML-сторінка)
не надає власного сигналу "що змінилось відколи ти заходила востаннє" — на
відміну від бази даних із колонкою `updated_at`. Тому доводиться:

1. Забирати весь список заново при кожному запуску.
2. Самостійно визначати, що з цього **реально нове чи змінене**, а що —
   просто повторний знімок того самого стану.
3. Помічати записи, які **зникли** з джерела (заклад закрився / сайт прибрав
   картку), не видаляючи історію фізично.

Це і є ручна реалізація патерну **hash-based change detection** — окремого
різновиду CDC (Change Data Capture), який застосовується саме тоді, коли
джерело не дає власного журналу змін.

## Джерела даних

Парсери для кількох українських довідників автосервісів:
top20.ua, list.in.ua, carta.ua, auto.ria.com, motointegrator.com, pzu.ua,
motul.ua. Кожен сайт має власну структуру сторінки — тому окремий парсер
на кожен, з подальшим об'єднанням і дедуплікацією результатів.

## Відоме обмеження
top20.ua показує для кожного міста фіксовану кількість закладів (≈200, 10 сторінок), і склад цього списку ротується з часом незалежно від того, чи заклад досі працює. Поточна реалізація mark_deleted позначає неактивним будь-який запис, відсутній в одному прогоні, що може хибно позначати тимчасово "витіснені" заклади як закриті. Плановане виправлення: позначати is_active = false тільки після кількох пропусків поспіль (missed_count), а не одразу.
## Архітектура пайплайну

```
[ Парсер сайту ]
        │  список записів (dict): name, city, street, phoneNumber
        ▼
[ record_id + scraped_at ]      ← стабільний ключ (MD5 від city+name+street)
        │                          + мітка часу "коли бачили"
        ▼
[ upsert_record() ]             ← для КОЖНОГО запису:
        │                          - новий record_id      → INSERT
        │                          - хеш змісту відрізняється → UPDATE,
        │                            updated_at оновлюється
        │                          - хеш той самий          → тільки
        │                            scraped_at оновлюється,
        │                            updated_at НЕ чіпається
        ▼
[ mark_deleted() ]               ← ОДИН раз в кінці прогону:
                                    record_id з бази, яких не було серед
                                    свіжих → is_active = false,
                                    deleted_at = зараз (soft delete,
                                    історія не втрачається)
```

Таблиця `raw_companies`:

| Колонка | Призначення |
|---|---|
| `record_id` | стабільний ключ запису (MD5) |
| `content_hash` | хеш "змістовних" полів, для порівняння змін |
| `scraped_at` | коли запис востаннє бачили на сайті |
| `updated_at` | коли дані **реально** змінились |
| `is_active` | чи запис досі є на сайті |
| `deleted_at` | коли запис зник (soft delete) |

## Що це демонструє

- Інкрементальне завантаження без доступу до `updated_at` на джерелі.
- Обробку всіх чотирьох станів CDC: додано / оновлено / без змін / видалено.
- Ідемпотентність: повторний запуск з тими самими даними не створює
  дублікатів і не змінює `updated_at` там, де нічого не змінилось.
- Перевірено тестовим сценарієм (`tests/test_full_pipeline.py`) на 4
  послідовних "днях" роботи скрапера.

## Стек

Python, `curl_cffi` (обхід Cloudflare), BeautifulSoup, PostgreSQL, `psycopg2`,
Docker (локальна база для тестів).
